# ADR-0033：远端分支只列配置过的远端

状态：Accepted

## Context

面板的「远程分支」来自 host 的 `git for-each-ref refs/remotes`（本地 ref，不联网）。这条查询把 `refs/remotes` 下每个非符号 ref 都当成分支，但 `refs/remotes` 并不等于「远端分支」：

- 工具/IDE 会把 GitLab 的合并请求 ref 抓进本地：`refs/remotes/mrs/<MR号>/head`、`.../merge`（实测仓库 `cargonova-be-logistics`：6948 条 refs 里 6916 条是这种 MR ref，其中 3474 条已合并）；
- 删掉一个远端后，它的 tracking refs 会留在 `refs/remotes/<remote>/…` 下；
- 这些 ref 不受任何**配置的 refspec** 覆盖，`git fetch --all --prune` 既不会更新也不会清理它们，只会一直堆积。

结果是分支区显示几千行「远程分支」，切换/删除入口也把它们当成可操作目标（对 `mrs/1/head` 切换会创建本地分支 `1/head`），既误导又拖慢快照（实测一次分支查询 JSON 约 620 KB）。

备选：

1. 只在客户端过滤 —— 数据仍全量过 RPC、仍要折树，只是少画几行；治标。
2. 按名称形状过滤 MR ref（`<x>/<数字>/(head|merge)`）—— 依赖命名习惯，对「删远端后残留」无效。
3. 列表照旧，加「隐藏孤儿」开关 —— 默认仍是几千行，且用户要先知道孤儿是什么。
4. 只提示用户手动清理 —— 面板显示问题没解决。

## Decision

- host 的分支查询新增一次 `git remote`，随后只保留**第一段是配置过的远端名**的 `refs/remotes` ref。归属判定用最长匹配（远端名可以含 `/`，`work/fork/topic` 属于 `work/fork` 而不是 `work`），由 `configuredRemoteOf` 实现。
- 没有配置任何远端时，远端分支列表就是空的——这是「没有远端」的正确投影，而不是把残留 ref 当分支。
- `git remote` 读取失败时**不过滤**（保持旧行为），因为「全部藏起来」比「露一条残留」更糟；只有明确拿到远端名单才过滤。
- 不引入 merged 判定、数量上限或 MR-ref 形状规则：本决策只回答「谁算远端分支」。已合并分支的标记/折叠是另一个问题（合并后远端分支依然存在，属于远端仓库的生命周期），需要时另立 ADR。
- 客户端（分支树、切换目标、复制/删除入口）不做改动：它们消费的 `remote` 列表已经是收窄后的结果，`ref` 字段仍在，切换/删除的完整引用路径不变。

## Consequences

- 实测仓库的远程分支从 6948 条降到 24 条，一次分支查询的 payload 相应下降；`mrs`/`mr` 这类残留 ref 不再出现在分支区，也不会被当作切换/删除目标。
- 代价：如果确实想从 MR ref 切分支/比较，面板里看不到了——需要先把它们抓成某个**已配置远端**下的引用，或使用别的工具。这是有意的取舍：面板把「远端分支」定义回 git 自己的 `remote` 概念。
- 残留 ref 仍然留在本地磁盘（本 ADR 不清理它们）；`--prune` 依旧管不到，用户需要时自行 `git update-ref -d`。
- 默认分支探测仍硬编码 `refs/remotes/origin/HEAD`（既有行为，不随本次收窄改变）；没有 `origin` 的仓库只是没有「默认分支」标记，远端分支列表本身仍然显示。
